## Booking Release Module — server/src/routes/bookings.ts (POST /:id/release)

Tested via `supertest` against a minimal standalone Express app mounting the real, unmodified `bookings.ts` router — same pattern as the auth suite, without importing `index.ts`. A real JWT was signed with the test `JWT_SECRET` (role `admin`) and sent as a bearer token, with `prisma.user.findUnique` mocked to satisfy the `authenticate`/`authorizeAdmin` middleware chain (which re-fetches the user from the DB on every request). One additional risk found during inspection: `bookings.ts` imports `lib/notifications.ts`, which itself does `import { io } from '../index'` — meaning importing the real `bookings.ts` router transitively pulls in `index.ts` (and its live-server/Socket.IO/background-job/Supabase side effects) unless `lib/notifications` is intercepted first. This was handled with an explicit `jest.mock('../../lib/notifications', () => ({ ... }))` **factory** (not a bare `jest.mock('../../lib/notifications')` automock) — a factory prevents Jest from ever requiring the real module, so `index.ts` is never loaded. No production file was modified to work around this; it's a test-only interception.

All 7 guard branches, their exact order, and the try/catch geofence-resilience behavior were confirmed by reading `bookings.ts` directly and matched the original inventory description exactly — no discrepancies found (see Section A of the report for the full confirmation).

**Step-1 inspection findings — this diverged from the task's framing in two significant ways:**
1. There are actually **two separate guards**, not one: an upstream `authenticate`-level guard (`booking.status !== 'ACTIVE' || !booking.trackingSession?.isActive` → hard `400` rejection, location never saved) which was **out of scope** for this round's "geofence-breach alerting block," and a separate, in-scope guard specifically gating the geofence check itself: `if (booking.geofenceActivatedAt && !booking.geofenceEndedAt)`. 2. **No real point-in-polygon check exists anywhere in the code.** The task's framing assumed a genuine polygon-containment algorithm existed alongside the circle check; it does not. This is a genuine, currently-dead-but-reachable gap: a manually-drawn polygon zone provides **no actual geofencing protection at all** — a vehicle could be anywhere on Earth and still register as "inside" such a zone. It doesn't currently cause a customer-facing bug in production (release-created zones are always circles via `computeGeofence`), but it's a real latent gap the moment an admin manually creates a polygon-only zone via the existing `/geofences` endpoint. WB-089 confirms and documents this exactly.
